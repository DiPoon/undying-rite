# 기술 설계서 (v0)

게임 규칙은 `docs/design.md`에 있습니다. 이 문서는 그 규칙을 어떤 구조로 구현하는지를 정합니다. 구조상의 결정(1~6절)을 바꾸려면 사용자 승인이 필요하고, 세부 구현은 이 문서의 의도 안에서 자유롭게 정합니다.

## 1. 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 게임 규칙, 서버, 클라이언트의 예측·보간 | Rust (stable) | 사용자가 직접 읽고 유지보수할 언어입니다. 상태 기계 위주인 규칙 코드에 `enum`과 빠짐없는 `match`가 잘 맞습니다. |
| 브라우저에서 규칙 실행 | WebAssembly (`wasm-bindgen`) | 클라이언트 예측은 서버와 같은 이동 코드를 돌려야 합니다. 같은 Rust 코드를 브라우저용으로 컴파일해서 규칙을 한 벌만 유지합니다. |
| 브라우저 껍데기 | TypeScript, Vite, PixiJS | 그리기, 입력 수집, WebSocket 연결, 화면 표시만 맡습니다. 테스터가 설치 없이 링크로 들어올 수 있어야 합니다. |
| 서버 런타임 | tokio, axum | 방 하나가 태스크 하나라는 구조에 맞고, HTTP 정적 파일과 WebSocket을 한 포트로 제공합니다. |
| 메시지 | serde, 우선 JSON | 브라우저 개발자 도구에서 읽을 수 있습니다. 인코딩은 한곳에서 바꿀 수 있게 둡니다. |
| 수치 설정 | TOML | 사람이 주석을 달아 가며 고칠 수 있습니다. |
| 테스트 | `cargo test`, `proptest` | 규칙 단위 테스트, 결정론 테스트, 무작위 상황 기반의 정보 누출 테스트에 씁니다. |

- **TypeScript 쪽에는 게임 규칙을 쓰지 않습니다.** 이동, 충돌, 시야, 판정, 타이머 계산이 TypeScript에 한 줄이라도 생기면 규칙이 두 벌이 됩니다. 껍데기는 Rust가 돌려준 값을 그리기만 합니다.
- 크레이트와 패키지의 버전은 기억에 의존하지 말고 설치 시점의 최신 안정판을 확인해 쓰고, `Cargo.lock`과 `package-lock.json`을 커밋합니다. Rust 버전은 `rust-toolchain.toml`로 고정하고 `wasm32-unknown-unknown` 타깃과 `rustfmt`, `clippy`를 함께 적습니다.
- WebAssembly 빌드 도구는 `wasm-bindgen` 계열 안에서 설치 시점에 유지보수되고 있는 것을 확인해 고릅니다. 사용법이 불확실하면 공식 문서를 확인합니다.
- 의존성은 꼭 필요한 것만 추가합니다. 게임 엔진, ECS 라이브러리는 쓰지 않습니다. 브라우저 껍데기에는 UI 프레임워크와 상태 관리 라이브러리를 쓰지 않습니다.

## 2. 저장소 구조

```
CLAUDE.md
Cargo.toml             워크스페이스
rust-toolchain.toml
docs/                  설계 문서
maps/                  맵 텍스트 파일
config/balance.toml    수치 원본 (design.md 12절에서 옮김)
scripts/               환경 준비, 전체 검사
crates/
  shared/              게임 규칙 전체, 프로토콜 타입, 설정과 맵의 파싱. 입출력 없음
  client-core/         예측과 보정, 보간, 서버 시각 추정. 입출력 없음
  client-wasm/         client-core를 브라우저에 내보내는 얇은 wasm-bindgen 래퍼
  server/              방 관리, 틱 루프, WebSocket, 봇, 기록
  tools/               화면 없는 시뮬레이터, 리플레이 검증, 테스트 클라이언트
web/                   브라우저 껍데기 (TypeScript, Vite, PixiJS)
```

의존 방향은 `client-core → shared`, `client-wasm → client-core`, `server → shared`, `tools → shared, client-core, server`뿐입니다. `shared`와 `client-core`는 네이티브와 `wasm32-unknown-unknown` 양쪽으로 컴파일되어야 하므로 파일, 네트워크, 시계, 스레드를 쓰지 않습니다.

## 3. shared: 시뮬레이션 계약

게임 규칙은 전부 `shared`에 있습니다. 이렇게 하는 이유는 넷입니다. 클라이언트 예측이 서버와 같은 코드를 돌립니다. 봇과 시뮬레이터가 네트워크 없이 같은 규칙을 돌립니다. 테스트가 서버를 띄우지 않고 규칙을 검증합니다. 기록된 입력으로 라운드를 똑같이 재현할 수 있습니다.

**핵심 함수** (이름과 정확한 모양은 구현하면서 정하되 역할은 유지합니다)

| 함수 | 역할 |
|---|---|
| `create_round(config, map, seed, players)` | 라운드 초기 상태를 만듭니다. |
| `step(state, inputs)` | 한 틱을 진행하고 그 틱에 일어난 사건 목록을 돌려줍니다. |
| `step_character(character, input, world)` | 캐릭터 한 명의 이동, 회전, 넘기, 공격 준비 동작을 한 틱 진행합니다. `step`이 내부에서 쓰고, 클라이언트 예측도 같은 함수를 씁니다. |
| `view_for(state, player_id)` | 그 플레이어가 알아도 되는 정보만 담은 화면용 상태를 만듭니다. design.md 11절의 표가 그대로 구현되는 곳입니다. |
| `hash_state(state)` | 상태 전체의 해시를 계산합니다. 결정론 테스트에 씁니다. |

**결정론 규칙**

같은 초기 상태와 같은 입력열을 주면 틱마다 같은 상태 해시가 나와야 합니다. 네이티브 빌드와 WebAssembly 빌드 사이에서도 같아야 합니다.

- `shared` 안에서 시계와 스레드 난수를 쓰지 않습니다. 난수는 상태에 들어 있는 시드 기반 생성기에서만 얻습니다.
- 시간은 틱 수로만 셉니다. 설정의 초 단위 값은 불러올 때 한 번 틱으로 환산합니다. 틱레이트를 30에서 60으로 바꿔도 규칙 코드를 고치지 않아도 되게 하기 위해서입니다.
- 순회 순서가 정해지지 않은 `HashMap`, `HashSet`을 규칙 처리에 쓰지 않습니다. 캐릭터와 물체는 식별자 순으로 처리합니다.
- 삼각함수처럼 플랫폼마다 구현이 다를 수 있는 수학 함수는 `libm` 크레이트의 것을 써서 네이티브와 WebAssembly의 결과를 맞춥니다.
- 그래도 클라이언트의 보정에는 작은 허용 오차를 둡니다(5절). 고정소수점은 쓰지 않습니다.
- `shared`와 `client-core`는 `unsafe`를 쓰지 않고, 바깥에서 들어온 값 때문에 패닉하지 않습니다. 잘못된 입력은 검증해서 오류 값으로 돌려줍니다.

**수치**

규칙 코드에 숫자를 직접 쓰지 않습니다. 모든 수치는 `config/balance.toml`에서 읽고, 불러올 때 범위를 검증합니다. 파일을 읽는 것은 서버와 도구의 몫이고 `shared`는 문자열을 받아 파싱만 합니다. 플레이테스트 중 수치를 계속 바꿔야 하므로, 서버는 재시작 없이 설정을 다시 읽어 다음 라운드부터 적용할 수 있어야 합니다.

## 4. 서버

**방**
- 방 하나가 태스크 하나이고 라운드 상태 하나를 소유합니다. 방은 채널로만 바깥과 통신합니다. 연결 태스크는 받은 메시지를 방의 채널로 넘기고, 방은 연결별 송신 채널로 내보냅니다. 방의 상태를 다른 태스크와 공유하지 않으므로 방 안에서 락은 필요 없습니다.
- 방의 상태는 대기실, 카운트다운, 진행, 결과 순으로 넘어가고 결과 뒤 대기실로 돌아갑니다.
- 입장은 방 코드로 합니다. 매치메이킹은 없습니다.
- 접속이 끊긴 플레이어의 자리는 정해진 시간 동안 유지하고(시작값 60초), 그동안 캐릭터는 입력 없음으로 처리합니다. 같은 플레이어가 재접속 토큰으로 돌아오면 이어서 합니다.
- 사람이 없는 방은 정리합니다.

**틱 루프**
- 고정 틱 30Hz입니다. 틱레이트는 설정값입니다.
- 타이머의 흔들림에 영향받지 않게 경과 시간을 누적해서 밀린 틱을 따라잡는 방식으로 돌립니다. 한 번에 따라잡는 틱 수에는 상한을 둡니다.
- 한 틱의 순서: 입력 수집, `step` 실행, 플레이어별 `view_for` 계산과 전송, 사건 전송, 기록.

**입력 처리**
- 클라이언트는 입력만 보냅니다. 위치나 판정 결과를 보내지 않으며, 서버는 그런 값을 받지도 않습니다.
- 입력에는 일련번호가 붙습니다. 서버는 플레이어마다 입력 대기열을 두고 틱당 하나씩 소비합니다. 대기열이 비면 직전 입력을 유지합니다. 대기열이 쌓이면 틱당 소비량을 조금 늘려 따라잡되, 실제 시간보다 빨리 움직일 수는 없게 상한을 둡니다.
- 받은 값은 전부 검증합니다. 이동 벡터의 크기, 숫자의 유한성, 메시지 크기, 초당 메시지 수.

**상태 전송과 시야**
- 서버는 매 틱 플레이어별로 `view_for`의 결과를 보냅니다. 보이지 않는 상대 진영 캐릭터는 메시지에 들어 있지 않습니다. 클라이언트를 뜯어 봐도 숨은 정보를 얻을 수 없어야 합니다.
- 사건(피격, 다운, 구속, 구출, 사망, 리스폰, 판자, 목표 완료 등)도 같은 기준으로 걸러서 보냅니다. 어떤 사건이 누구에게 가는지는 design.md 11절을 따릅니다.
- 살인마에게 보내는 생존자 식별자는 design.md 11절의 익명화 규칙을 따릅니다.
- 매 틱 전체 상태를 보내는 것으로 시작합니다. 개체가 적어서 차이만 보내는 압축은 필요 없습니다.

**봇**
- 봇은 서버 안에서 돌지만 사람과 똑같이 `view_for`가 준 정보만 보고 입력을 만듭니다. 전체 상태를 직접 읽지 않습니다. 봇이 시야 규칙을 우회하면 시야 필터의 버그를 봇 테스트로 잡을 수 없기 때문입니다.
- 첫 버전의 봇은 단순합니다. 생존자 봇은 가까운 활성 목표로 가서 작업하고, 살인마가 가까이 보이면 달아나고, 근처 아군을 구출·소생·치료합니다. 살인마 봇은 활성 목표를 돌다가 보이는 생존자를 쫓아가 공격하고 다운된 생존자를 구속합니다.
- 길 찾기는 타일 격자 위의 A*면 충분합니다.

**정적 파일**
- 배포 형태에서는 서버 실행 파일 하나가 빌드된 브라우저 껍데기와 WebSocket을 같은 포트로 제공합니다.

## 5. 클라이언트

클라이언트는 세 층입니다. 판단이 필요한 로직은 전부 Rust에 있고, TypeScript는 화면과 입력 장치에 닿는 부분만 맡습니다.

| 층 | 언어 | 맡는 일 |
|---|---|---|
| `client-core` | Rust | 서버 메시지 해석, 자기 캐릭터 예측과 보정, 다른 캐릭터 보간, 서버 시각 추정, 시야 밖 영역 계산, 화면에 그릴 상태 만들기 |
| `client-wasm` | Rust | `client-core`를 브라우저에 내보내는 래퍼. 로직 없음 |
| `web` | TypeScript | WebSocket 연결, 키보드·마우스 입력 수집, PixiJS로 그리기, 화면 표시, 접속과 대기실 화면 |

`client-core`가 네이티브로도 컴파일되기 때문에, 화면 없는 테스트 클라이언트(`tools`)는 브라우저와 똑같은 예측 코드를 돌립니다. 브라우저 없이 예측 오차를 잴 수 있는 것이 이 구조의 이점입니다.

**Rust와 TypeScript의 경계**
- 경계는 굵게 잡습니다. 프레임마다 호출 몇 번이면 충분합니다. 대략 다음과 같습니다: 받은 메시지를 넘긴다, 현재 입력을 넘긴다, 시간을 진행시키고 보낼 메시지를 돌려받는다, 화면에 그릴 상태를 돌려받는다, 디버그 수치를 돌려받는다.
- WebSocket은 TypeScript가 소유하고, 받은 내용을 해석하지 않고 그대로 Rust에 넘깁니다.
- 화면에 그릴 상태에는 위치, 방향, 겉모습 상태, 시야 밖 영역, 표시할 수치가 이미 계산되어 들어 있어야 합니다. TypeScript가 그 값으로 다시 계산해야 한다면 경계를 잘못 그은 것입니다.

**예측과 보정**
- 자기 캐릭터만 예측합니다. 입력을 보내는 즉시 `step_character`로 자기 캐릭터를 진행하고, 보낸 입력을 보관합니다.
- 서버 상태가 오면 자기 캐릭터를 서버 값으로 되돌린 뒤, 서버가 아직 처리하지 않은 입력(서버가 알려 준 일련번호 이후)을 다시 적용합니다.
- 다시 적용한 결과와 화면에 그리던 위치의 차이가 작으면 짧은 시간에 걸쳐 부드럽게 맞추고, 크면 즉시 맞춥니다. 문턱값은 설정값입니다.
- 넘기와 판자 내리기는 시작 동작만 미리 보여 줍니다. 피격, 기절, 다운, 구속, 구출 완료, 사망은 서버가 확정한 뒤에만 표시합니다. 결과를 미리 보여 줬다가 취소되는 것이 가장 나쁜 경험이기 때문입니다.
- 다른 캐릭터와의 충돌은 예측에 포함하되, 상대 위치는 화면에 그려진 위치를 씁니다. 여기서 생기는 오차는 보정으로 흡수합니다. 이 부분은 지연이 클 때 떨림이 생기기 쉬운 곳이므로 보정 크기를 기록해 확인합니다.

**보간**
- 다른 캐릭터는 약 100ms 과거의 상태를 두 서버 상태 사이에서 보간해 그립니다. 지연 시간은 설정값입니다.
- 서버 시각은 왕복 지연 측정으로 추정합니다.

**화면**
- 그림은 도형입니다. 캐릭터는 원과 방향 표시, 타일은 색 사각형입니다.
- 자기 시야 밖은 어둡게 덮습니다. 이 영역은 서버 판정과 같은 `shared`의 시야 함수로 계산해서, 화면에 밝게 보이는 곳과 서버가 보여 주는 곳이 어긋나지 않게 합니다.
- 화면에 보이는 세계 크기는 고정이고, 화면 비율이 다르면 남는 부분을 가립니다.
- 표시할 것: 남은 시간, 사망 횟수, 목표 진행, 자기 상태와 수명 게이지, 접근 경고, 생존자에게는 아군의 위치·상태·게이지, 살인마에게는 공격 후딜 표시, 사망자에게는 리스폰 지점 선택.
- 글자는 PixiJS가 아니라 HTML 요소로 그립니다. 한글 표시가 추가 작업 없이 됩니다. 화면에 나오는 문자열은 `web`의 한 파일에 모읍니다.

## 6. 프로토콜

메시지의 종류와 방향만 정합니다. 필드는 구현하면서 정하고 `shared`에 타입으로 둡니다. 서버와 `client-core`가 같은 타입을 쓰므로 TypeScript 쪽에 메시지 타입을 따로 쓰지 않습니다.

| 방향 | 메시지 | 내용 |
|---|---|---|
| 클라이언트 → 서버 | 입장 | 방 코드, 이름, 재접속 토큰(있으면) |
| | 대기실 조작 | 역할 선택, 준비, 시작 |
| | 입력 | 일련번호, 이동 방향, 조준 방향, 버튼 상태 |
| | 리스폰 선택 | 리스폰 지점 |
| | 지연 측정 | 클라이언트 시각 |
| 서버 → 클라이언트 | 환영 | 플레이어 식별자, 재접속 토큰, 틱레이트, 수치 설정, 맵 |
| | 대기실 상태 | 참가자와 역할 |
| | 라운드 시작 | 자기 역할, 시작 틱 |
| | 상태 | 틱, 처리한 마지막 입력 일련번호, 자기 캐릭터 전체 상태, 보이는 캐릭터들, 물체 상태, 점수와 시간 |
| | 사건 | 그 플레이어가 알아도 되는 사건 |
| | 라운드 종료 | 승자, 진행률, 요약 지표 |
| | 지연 측정 응답 | 클라이언트 시각, 서버 틱 |

- 프로토콜 버전을 환영 메시지에 넣고, 맞지 않으면 접속을 거절합니다.
- 라운드 시드는 클라이언트에 보내지 않습니다. 목표 활성화 순서 같은 미래 정보가 새기 때문입니다.

## 7. 개발 환경에서 확인된 사실

이 저장소는 WSL 안에서 Windows 드라이브(`/mnt/e`, NTFS)에 놓여 있습니다. 2026-11-27에 측정한 결과입니다. 느린 원인은 드라이브 자체가 아니라 WSL이 Windows 파일시스템에 접근하는 경로이므로, `/mnt/` 아래의 다른 드라이브도 마찬가지입니다. WSL 홈 디렉터리처럼 리눅스 가상 디스크 안에 있는 경로는 빠릅니다.

| 항목 | `/mnt/e` 에서의 결과 | 영향 |
|---|---|---|
| 작은 파일 쓰기 | 파일당 약 21ms (리눅스 쪽의 약 240배) | 빌드 산출물을 여기에 두면 빌드가 쓸 수 없을 만큼 느려집니다. |
| 작은 파일 읽기 | 파일당 약 4ms | 소스를 읽는 정도는 감당할 수 있습니다. |
| 파일 감시 | WSL 쪽에서 고친 파일은 감지됨. Windows 쪽 편집기로 고친 파일은 감지되지 않음 | Vite에 폴링 감시를 켜는 환경 변수를 마련해 둡니다. |
| 대소문자 | 구분하지 않음 | 이름이 대소문자만 다른 파일을 만들지 않습니다. 경로의 대소문자가 틀려도 여기서는 동작하고 배포 환경에서 깨집니다. |
| 파일 권한 | `chmod`가 적용되지 않음 (항상 777) | `git config core.fileMode false`를 설정하고, 스크립트는 `bash scripts/이름.sh`로 실행합니다. |
| 심볼릭 링크 | 동작함 | 아래의 `target` 연결에 씁니다. |

**빌드 산출물은 리눅스 쪽에 둡니다.** 소스는 이 저장소에 그대로 두고, Cargo의 `target` 디렉터리만 WSL 홈 아래(예: `~/.cache/undying-rite/target`)에 만든 뒤 저장소의 `target`을 그곳을 가리키는 심볼릭 링크로 둡니다. `target`은 저장소에 올리지 않습니다. 이 준비는 `scripts/`의 스크립트 하나로 되게 하고, 산출물이 실제로 리눅스 쪽 파일시스템에 쌓이는지 확인합니다. `web/node_modules`는 처음에는 저장소 안에 두고 설치 시간(몇 분)을 감수합니다.

**도구.** 설치되어 있는 것: Node 24.15, npm 11.12, git 2.56, gh. Rust는 설치되어 있지 않으므로 `rustup`으로 설치합니다. 툴체인은 `~/.rustup`과 `~/.cargo`에 들어가고 셸 프로필에 경로가 추가됩니다. 디스크는 툴체인에 1GB 남짓, 빌드 산출물에 몇 GB를 씁니다(어림값). 모두 WSL 가상 디스크 안입니다.

**M0에서 잰 것** (2026-11-27~28)

| 항목 | 결과 | 영향 |
|---|---|---|
| 디스크 사용 | `~/.rustup` 723MB(1.100.0 하나), `~/.cargo` 254MB(레지스트리, wasm-bindgen-cli), `target` 2.3GB, `web/node_modules` 156MB(`/mnt/e`). WSL 가상 디스크는 C:에 있음 | C: 여유 공간에서 빠집니다. `target`은 `cargo clean`으로 비울 수 있습니다. |
| 첫 빌드 시간 | `shared` 테스트 첫 빌드 3분, 워크스페이스 테스트 첫 빌드 약 4분30초, wasm 릴리스 빌드 30초, `wasm-bindgen-cli` 설치 수 분, `npm install` 2~3분 | 처음 한 번만 깁니다. |
| 타이머 정밀도 | 평소 `sleep(33ms)`가 p99 0.25ms 늦게 깸. 다른 무거운 작업(같은 기기의 다른 세션이 `zstd -T0`으로 전 코어를 쓰던 때)이 돌면 p90 30ms, 최대 67ms 늦게 깸 | 그때 서버 틱이 몰리고 화면 없는 시험의 예측 오차가 흔들립니다. 시험 결과가 이상하면 `top`으로 다른 부하부터 봅니다. |
| Windows 쪽 부하 | 2026-11-28 새벽, Windows CPU 사용률 80%(다른 프로그램)일 때 WSL 안은 유휴로 보이는데도 CPU 1.2초짜리 계산이 10~12초 걸림(벽시계의 약 10%만 받음), `/mnt/e` 파일 읽기 380ms. 서버 틱 간격 최대 0.2~2.5초 | WSL 안의 `top`에는 드러나지 않습니다. 이때의 시간 기반 시험(화면 없는 시험, 연기 시험의 왕복 지연)은 의미가 없습니다. `python3 -c 'sum(range(30_000_000))'`이 1~2초 안에 끝나는지로 확인합니다. 화면 없는 시험은 이 상황을 감지하면 판정 아래에 경고를 붙입니다. |
| WSL과 Windows의 시계 빠르기 | WSL의 단조 시계가 Windows 시계(QPC)보다 2.5~3.4% 느림. 서버가 Windows 기준 초당 약 29틱을 돎 | 브라우저(Windows)와 서버(WSL)의 시계가 다릅니다. 클라이언트가 서버 틱 속도를 재서 맞추고(`client-core`의 `RateEstimator`), 디버그 표시의 "서버 틱 속도"로 볼 수 있습니다. |
| 네트워크 | WSL은 NAT 모드. 127.0.0.1에 띄운 서버가 Windows 브라우저의 `localhost:포트`로 열림. 이 중계를 거친 상태 메시지의 도착 흔들림은 지연 주입 없이 약 30ms | 서버를 0.0.0.0에 띄우지 않아도 됩니다. |
| 브라우저 | Windows에 Edge가 있고 Chrome은 없음. Edge를 headless로 띄우고 개발자 도구 프로토콜로 키를 눌러 화면을 찍을 수 있음 | 사람 확인 전에 그리기가 되는지 자동으로 볼 수 있습니다. headless는 수직 동기화가 없어 240FPS로 돕니다. |

## 8. 테스트와 검증 수단

화면을 보고 손으로 해 보는 것만으로는 검증할 수 없으므로, 아래 수단을 마일스톤마다 갖춰 나갑니다.

| 수단 | 확인하는 것 |
|---|---|
| 규칙 단위 테스트 | 이동과 충돌, 시야 판정, 공격 판정, 수명 게이지, 상호작용, 판자와 창틀, 목표, 리스폰, 승패 판정. design.md의 규칙 하나하나가 테스트 하나 이상에 대응합니다. |
| 결정론 테스트 | 같은 시드와 입력으로 두 번 돌려 틱마다 해시가 같은지 확인합니다. |
| 네이티브와 WebAssembly의 일치 | 정해진 입력열을 WebAssembly 빌드로도 돌려(Node에서 실행) 네이티브와 최종 해시가 같은지 확인합니다. |
| 정보 누출 테스트 | 무작위 상황을 많이 만들어, `view_for`의 결과에 그 플레이어가 알면 안 되는 값이 들어 있지 않은지 확인합니다. |
| 화면 없는 라운드 | 모든 자리를 봇으로 채운 라운드를 최대 속도로 끝까지 돌려, 멈추거나 패닉하지 않는지와 지표를 확인합니다. |
| 지연 주입 | 서버가 연결별로 보내고 받는 메시지를 지정한 만큼 늦추는 옵션을 둡니다. 화면 없는 테스트 클라이언트가 이 옵션 아래에서 예측 오차를 잽니다. |
| 리플레이 검증 | 기록된 라운드를 다시 돌려 최종 해시가 기록과 같은지 확인합니다. |

전체 검사는 스크립트 하나로 돌립니다: 포맷 검사, `clippy`(경고를 오류로), 워크스페이스 테스트, WebAssembly 빌드, `web`의 타입 검사, 화면 없는 라운드. 작업을 마쳤다고 보고하기 전에 반드시 통과시킵니다.

## 9. 기록과 지표

- 방마다 라운드의 시드, 수치 설정, 맵, 틱별 입력, 최종 해시를 파일로 남깁니다(한 줄에 JSON 하나). 저장 위치는 `var/` 아래이고 저장소에는 올리지 않습니다.
- 라운드가 끝나면 design.md 15절의 지표를 계산해 요약으로 남깁니다. 플레이테스트의 판단 근거가 됩니다.

## 10. 지금 하지 않는 것

필요해졌다는 근거가 생기기 전에는 만들지 않습니다.

- 데이터베이스, 계정, 인증, 결제
- 이진 프로토콜, 차이만 보내는 상태 압축, UDP 계열 전송
- 공격 판정의 지연 보상(피격 대상 위치 되감기). 공격 준비 동작 시간이 지연을 흡수하는 것으로 시작합니다.
- 여러 프로세스나 여러 지역에 걸친 확장, 컨테이너 구성
- 화면 전체를 Rust로 그리는 클라이언트
- 외부에 공개되는 배포. 배포가 필요해지면 방식과 시점을 사용자와 정합니다.
