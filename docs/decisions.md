# 결정 기록

규칙이나 구조 문서가 비어 있던 곳을 구현하면서 어떻게 메웠는지의 기록입니다 (design.md 13절). 사용자가 승인한 항목은 원래 문서에 반영하고 여기에 "반영함"으로 표시합니다.

형식: 무엇이 비어 있었는지 / 어떻게 정했는지 / 다르게 정할 수 있었던 안

## 2026-11-27 (M0)

### 게임 규칙 (design.md)

**M0 캐릭터의 속도와 크기**
- 빈 곳: M0는 "모두 같은 속도로 움직이는 원"이라고만 되어 있고 값이 없음.
- 정함: 생존자 값(`survivor.run_speed` 4.0, `survivor.radius` 0.35)을 모든 캐릭터에 씀. 역할은 M1에서 나눔.
- 다른 안: 살인마 값, 또는 M0 전용 설정값.

**M0 캐릭터끼리의 충돌**
- 빈 곳: 5절은 살인마–생존자는 막고 생존자끼리는 통과한다고 정하지만, M0에는 역할이 없음.
- 정함: 캐릭터끼리 충돌하지 않음 (모두 생존자로 보아 통과). 마일스톤의 확인 항목도 "지형 충돌만 있는 상황"을 전제로 함. 살인마–생존자 충돌은 M1에서 만듦.
- 다른 안: M0부터 모두 서로 막기.

**살인마 시작 지점(K)의 개수**
- 빈 곳: 4절은 K의 수가 12절과 맞는지 검사하라고 하지만 12절에 K의 수가 없음.
- 정함: 정확히 1개. 살인마가 1명이라는 게임 정의에서 나오는 값이라 설정 파일에 두지 않고 `shared/src/map.rs`의 상수로 둠.
- 다른 안: 설정값으로 두기.

**창틀·판자 자리 검사의 "바닥"과 "벽"**
- 빈 곳: "마주 보는 두 이웃이 바닥이고 나머지 두 이웃이 벽"에서 바닥과 벽의 범위.
- 정함: 바닥 = 걸을 수 있는 타일(`.` `O` `R` `S` `K`). 벽 = 이동을 막는 고정 타일(`#` `=` `-`). 창틀 옆에 창틀이나 판자 자리가 붙는 배치(폭 2칸 창틀 등)는 허용하지 않음.
- 다른 안: 벽을 `#`, `=`로만 한정, 또는 폭 2칸 창틀 허용.

**판자 자리(P)의 M0 상태**
- 빈 곳: 판자의 처음 상태와 내리기 규칙은 8절(M1 범위).
- 정함: M0에서는 판자가 서 있는 상태로 보고 지나갈 수 있게 함.

**시작 위치와 방 정원**
- 빈 곳: 대기실과 역할이 없는 M0에서 누가 어디서 시작하는지.
- 정함: 방 정원은 `round.survivor_count + 1`(4명). 들어온 순서대로, 반경 1m 안에 다른 캐릭터가 없는 첫 S 지점(위에서 아래, 왼쪽에서 오른쪽 순)에 놓고, 모두 차 있으면 첫 S 지점에 놓음.

### 구조 (architecture.md 4~6절의 세부)

**입력 대기열: "대기열이 비면 직전 입력을 유지"의 해석** (`server/src/input_queue.rs`)
- 빈 곳: 직전 입력을 유지한 틱과, 그 뒤 늦게 도착한 입력의 관계.
- 정함: 서버 틱 하나를 입력 일련번호 하나의 칸으로 봄. 대기열이 비면 직전 입력을 다음 번호의 칸에 대신 쓰고, 그 번호의 입력이 늦게 오면 버림. 같은 키를 누르고 있는 동안에는 서버와 클라이언트 예측이 같은 입력을 쓰게 되어 예측이 어긋나지 않음.
- 다른 안: 칸을 쓰지 않고 직전 입력을 한 번 더 적용한 뒤 늦은 입력도 적용(이 방식은 대기열이 빌 때마다 서버가 한 걸음 더 가서 예측이 반드시 어긋남. 실제로 처음 구현했을 때 13.3cm 오차가 났음).

**오래 멈춘 클라이언트**
- 정함: 직전 입력을 대신 쓰는 것이 4틱(`net.input_max_substitute`) 넘게 이어지면 멈춤 입력으로 바꾸고 버퍼가 다시 찰 때까지 기다림. 탭이 숨겨지거나 창이 멈췄을 때 캐릭터가 계속 달려가지 않게 하려는 것임. 브라우저는 창이 포커스를 잃으면 모든 키를 뗀 것으로 보냄.
- 다른 안: 끝까지 직전 입력 유지.

**입력 버퍼의 크기와 조절**
- 정함: 시작 버퍼는 3틱(`net.input_buffer_target`). 2틱일 때 150±30ms 지연에서 60초 시험 중 위상이 나쁜 클라이언트가 최대 3.9cm 어긋났음(망 흔들림 ±15ms에 브라우저 프레임 간격 16.7ms가 더해짐). 대신 쓰기가 생기면 버퍼를 한 칸 늘리되, 그 플레이어가 멈춰 서 있어서 한 틱을 더 끼워도 상태가 그대로인 순간(서버가 `step_character`로 직접 확인)에만 늘림. 10초(`net.input_buffer_shrink_after`) 동안 문제가 없으면 한 칸씩 되돌림.
- 대가: 다른 플레이어가 나를 보는 시점이 2틱일 때보다 33ms 늦음. 자기 캐릭터는 예측으로 바로 움직이므로 조작감에는 영향이 없음.
- 다른 안: 2틱 고정(지연이 작지만 예측 오차가 남음), 클라이언트가 서버 대기열 깊이를 받아 자기 틱 속도를 조절하는 방식(더 정확하지만 프로토콜과 제어 루프가 늘어남).

**클라이언트의 틱 속도를 서버 시계에 맞춤** (`client-core/src/clock.rs`의 `RateEstimator`)
- 빈 곳: 문서는 클라이언트가 서버와 같은 틱레이트로 입력을 만든다고 전제함.
- 발견: 이 개발 환경에서 WSL의 시계가 Windows 시계보다 2.5~3.4% 느림(architecture.md 7절). 브라우저는 Windows 시계로 초당 30개 입력을 보내는데 서버는 Windows 기준 초당 약 29틱만 돌아서, 서버 입력 대기열이 계속 불어나고(브라우저에서 확인 대기 입력 19개) 보간도 멈춤(전체 21.7%).
- 정함: 클라이언트가 최근 10초의 상태 도착 시각과 틱으로 서버 틱 속도를 재서(명목값 ±5%로 제한), 로컬 예측 틱과 보간 재생 시각을 그 속도로 진행함. 서버는 그대로 기준 시계임. 화면 없는 시험에 시계가 ±2.5% 다른 클라이언트를 넣어 자동으로 확인함.
- 결과: 같은 브라우저 경로에서 보간 멈춤 0.1%, 확인 대기 입력 6개, 예측 오차 0.
- 다른 안: 서버가 대기열 깊이를 알려 주고 클라이언트가 속도를 조절하는 닫힌 제어.

**밀린 프레임을 한꺼번에 따라잡을 때의 입력**
- 정함: 클라이언트가 멈췄다가 여러 틱을 한꺼번에 진행할 때 마지막 틱만 지금 키를 쓰고 앞의 틱들은 직전 입력을 씀. 멈춘 동안에는 화면도 그려지지 않아 키가 언제 바뀌었는지 알 수 없고, 서버도 늦은 칸을 직전 입력으로 채우므로 이렇게 해야 서로 같음.

**보간 재생 시각**
- 정함: 창(2초) 안에서 가장 빨리 온 상태보다 `client.interp_delay`(100ms) 뒤, 그리고 가장 늦게 온 상태보다 한 틱 뒤 중 더 늦은 쪽. 도착이 고르면 설정한 지연 그대로이고 흔들림이 크면 그만큼 더 늦춤. 재생 속도는 ±10% 안에서만 바꾸고, 이미 멈춰 있으면 −50%까지 늦춤.

**작은 예측 오차의 화면 보정**
- 정함: 차이를 화면 오프셋으로 옮긴 뒤 시간 상수 `client.correction_smoothing`(0.1초)로 줄임. `client.correction_snap`(1m)보다 크면 즉시 맞춤.

**지연 주입의 뜻**
- 정함: `lag_ms`는 왕복 지연. 보내고 받는 쪽 각각 절반씩 늦추고, 흔들림은 편도마다 ±jitter/2(왕복 최대 ±jitter). WebSocket은 TCP라 순서가 바뀌지 않으므로 앞 메시지보다 먼저 도착하지 않게 함. 연결마다 `/ws?lag_ms=150&jitter_ms=30`으로 정하고(브라우저 주소의 `?lag=150&jitter=30`을 그대로 넘김), 서버 기본값은 `--lag-ms`, `--jitter-ms`.

**지연 측정 응답의 서버 틱**
- 정함: 방이 응답할 때 `마지막 틱 + 그 틱 시작 뒤 지난 시간`으로 소수까지 보냄. 방은 메시지를 틱 사이에 바로 처리하므로 틱 경계까지 기다리지 않음.

**설정 다시 읽기**
- 빈 곳: "재시작 없이 다음 라운드부터" — M0에는 라운드가 없음.
- 정함: 방을 새로 만들 때마다 `config/balance.toml`과 맵을 다시 읽음. 읽기에 실패하면 그 방은 만들지 않고 입장을 거절(`server_error`)하며 서버 로그에 이유를 적음.

**환영 메시지의 내용**
- 정함: 수치 설정과 맵은 파싱한 값이 아니라 원문 텍스트로 보내고 클라이언트도 같은 파서로 읽음. 틱레이트는 설정 안에 있으므로 따로 보내지 않음. 재접속 토큰은 M2에서 더함.

**방 코드와 이름**
- 정함: 방 코드는 영문자와 숫자 1~12자이고 대문자로 맞춤. 이름은 앞뒤 공백을 뺀 1~16자, 제어 문자 불가.

**네트워크·클라이언트 조정값의 위치**
- 정함: 서버 입력 대기열, 메시지 제한, 클라이언트 예측·보간 수치도 `config/balance.toml`의 `[net]`, `[client]` 절에 둠 (CLAUDE.md "수치를 코드에 직접 쓰지 않습니다"). 포트, 정적 파일 위치 같은 실행 옵션은 서버 명령줄 인자로 둠.

**화면 비율**
- 정함: 화면이 16:9보다 넓으면 좌우를 가리고, 좁으면 위아래는 가리지 않고 세계 높이 24m를 그대로 보여 줌(가로로 덜 보임).

**TypeScript와 Rust의 경계에서 TS가 하는 일**
- 정함: TS는 눌린 키(위·아래·왼쪽·오른쪽 불값)와 포인터 픽셀 좌표를 넘기고, Rust가 준 카메라 변환(scale, origin), 캐릭터 위치·방향·반지름, 이름표의 화면 좌표, 맵의 행 배열을 그대로 그림. 이동 방향, 조준 각도, 화면 비율 맞춤, 이름표 위치 계산은 모두 Rust에 있음. `scripts/check.sh`가 `web/src`에 `Math.*`, 삼각함수, 타이머 호출이 생기면 실패하게 함. 그리기 데이터의 모양(`web/src/types.ts`)은 TS에 한 벌 더 적혀 있음(메시지 타입은 아님).

### 도구

**툴체인과 빌드 도구**
- Rust는 `rust-toolchain.toml`에 1.100.0으로 고정(설치 시점의 stable). 같은 버전이 `stable`로 한 벌 더 깔리는 것을 막으려고 rustup 기본값을 1.100.0으로 바꾸고 `stable`을 지움.
- WebAssembly는 wasm-pack 대신 `wasm-bindgen-cli`를 직접 씀(둘 다 `wasm-bindgen` 조직이 2026-10-30에 릴리스, wasm-pack도 안에서 이것을 받아 씀). 버전은 `Cargo.lock`의 `wasm-bindgen`과 같아야 하므로 `scripts/setup.sh`가 맞춰 설치함.
- TypeScript는 설치 시점 최신판 7.0.2(Go로 다시 쓴 컴파일러)를 씀. 타입 검사와 빌드에 문제가 없었음.
- tools의 `tokio-tungstenite`는 axum 0.8.9가 쓰는 0.29에 맞춤(최신 0.30을 쓰면 같은 라이브러리가 두 벌 컴파일됨).

## 2026-11-28 (M0, PR #1 리뷰 반영)

**설정 파일에 두는 수치와 코드 상수의 경계**
- 빈 곳: CLAUDE.md "수치를 코드에 직접 쓰지 않습니다"가 어디까지인지.
- 정함: 게임 규칙의 수치, 그리고 네트워크·예측·보간의 동작을 바꾸는 조정값은 `config/balance.toml`에 둠. 이번에 옮긴 것: 시작 지점 점유 거리(`respawn.occupied_distance`), 보간 재생(`client.interp_arrival_window`, `interp_rate_adjust`, `interp_starved_slowdown`, `interp_snap`), 서버 틱 속도 추정(`client.rate_window`, `rate_min_span`, `rate_max_deviation`), 버리는 프레임 간격(`client.max_frame_gap`), 연결 제한(`net.message_burst`, `send_queue_max`, `write_timeout`).
- 코드 상수로 남기는 것: 디버그 표시용 창 길이(최근 5초 최대 오차 등), 메모리 상한(보관할 스냅숏 수 등), 수치 계산의 허용 오차와 반복 횟수(`PENETRATION_EPSILON`, `RESOLVE_ITERATIONS`, `MAX_SUBSTEPS`), 단위(`CREDIT_UNIT`), 안전 상한(`MAX_LAG_MS`), 설정 검증의 여유 비율(`MESSAGE_RATE_MARGIN`). 플레이테스트에서 바꿀 일이 없거나 바꾸면 계산이 깨지는 값들임.

**메시지 수 제한은 토큰 버킷**
- 정함: 1초 고정 창 대신, 초당 `net.max_messages_per_second`씩 차고 `net.message_burst`(600)까지 모이는 토큰 버킷. 망이나 서버가 몇 초 멈췄다 풀리면 쌓인 정상 메시지가 한꺼번에 읽히는데, 멈춘 시간만큼 토큰도 차 있어서 끊기지 않음.
- 교차 검사: `max_messages_per_second`는 정상 클라이언트의 송신량(틱레이트 × (1 + `rate_max_deviation`) + 1/`ping_interval`)의 1.5배 이상이어야 함. 그렇지 않으면 설정을 읽을 때 오류.

**보내는 길의 상한**
- 정함: 방 → 지연선 → 소켓의 모든 단계가 유계(`net.send_queue_max`)이고, 소켓 쓰기 하나에 `net.write_timeout`(5초) 제한을 둠. 상대가 읽지 않으면 지연선이 차서 방의 `try_send`가 실패하고 그 플레이어를 내보냄. 쓰기가 끝나면 그 연결의 읽기도 끝냄.

**연결 제한값의 적용 시점**
- 정함: `[net]`의 연결 제한값은 방에 들어가기 전(입장 메시지 크기, 입장 대기 시간)부터 쓰이므로 서버를 띄울 때 한 번만 읽음. 바꾸려면 재시작. CLAUDE.md, 서버 사용법, `balance.toml` 주석에 적음.

**지연 주입 기본값**
- 정함: 브라우저와 `tools bots`는 주소나 옵션에 `lag`/`jitter`가 있을 때만 서버에 넘김. 없으면 서버의 `--lag-ms`, `--jitter-ms`가 적용됨. 전에는 항상 0을 넘겨서 서버 기본값이 브라우저에 적용되지 않았음.

## 2026-11-28 (M0, PR #1 두 번째 리뷰 반영)

**건너뛴 틱 뒤의 입력 대기열**
- 빈 곳: 서버가 `net.max_catchup_ticks`를 넘게 밀려 틱을 건너뛰면, 그동안 입력은 실제 시간대로 도착하는데 소비 여유분은 쌓이지 않아 밀린 입력이 수십 초 동안 남았음.
- 정함: 건너뛴 틱 수만큼 "따라잡기 허용량"을 줌. 대기열이 목표보다 길 때 한 틱의 두 번째 입력부터만 쓰이고, 대기열이 목표 이하가 되면 버림. 건너뛴 시간은 실제로 흐른 시간이라 "실제 시간보다 빨리 움직이지 못함"과 부딪히지 않음.
- 다른 안: 대기열을 목표 길이까지 잘라 내기(예측이 그만큼 어긋남).

**`net.input_burst` 하한 2.0**
- 정함: 한 틱에 입력을 둘 쓰려면 여유분이 입력 두 개분은 모여야 하므로 2.0 미만은 설정 오류. 그 아래로는 따라잡기가 사라져 클라이언트 시계가 조금만 빨라도 대기열이 넘침.

**실행 중 다시 읽은 설정과 연결 한도**
- 정함: 방을 만들 때 다시 읽은 설정의 정상 송신량을, 그 파일의 값이 아니라 서버를 띄울 때의 `max_messages_per_second`와 비교함. 모자라면 방을 만들지 않고 "서버를 다시 띄워야 바뀝니다"라고 로그에 적음. 빈 방을 닫는 시간도 서버를 띄울 때의 `join_timeout`으로 정함(연결의 입장 대기와 맞춤).

**클라이언트의 시각 입력**
- 정함: `client-core`의 `update`와 `on_message`는 유한하지 않은 `now_ms`를 세션에 넘기지 않음. `update`는 그 프레임을 건너뛰고, `on_message`는 오류를 돌려줌.

**시간이 드는 테스트**
- 정함: 지연선 테스트는 tokio 가상 시간(`start_paused`)으로 돌려 벽시계와 기기 부하에 영향받지 않게 함. 이를 위해 server의 개발용 의존성에서만 tokio `test-util`을 켬.
