# 마일스톤

**현재 상태: M0 완료 (사람 확인은 사용자 결정으로 생략, 2026-11-28). 다음은 M1** (작업 세션이 끝날 때마다 이 줄과 체크박스, 맨 아래 진행 기록을 고칩니다)

첫 플레이 가능 버전이 답해야 할 질문은 하나입니다. "공유 목숨 풀, 리스폰, 구출이 네 명(살인마 1, 생존자 3)이 할 때 재미있는가." 이 질문에 답하는 데 필요 없는 것은 만들지 않습니다.

각 마일스톤에는 확인 항목이 두 종류 있습니다.

- **자동 확인**은 작업하는 쪽이 직접 돌려서 통과시키고, 보고에 실제 출력을 붙입니다.
- **사람 확인**은 조작감이나 재미처럼 사람이 해 봐야 아는 것입니다. 작업하는 쪽은 이것을 통과했다고 주장하지 않습니다. 대신 사용자가 바로 해 볼 수 있게 실행 방법과 볼 지점을 보고에 적습니다.

마일스톤은 순서대로 진행하고, 사용자가 사람 확인을 마친 뒤 다음으로 넘어갑니다.

---

## M0. 네트워크 골격

**목적:** 서버 권위 구조에서 이동이 지연 속에서도 매끄러운지 확인합니다. 이후의 모든 것이 이 위에 올라가므로, 여기서는 게임 규칙보다 구조를 바르게 잡는 것이 중요합니다.

**작업**
- [x] Rust 툴체인 설치(`rustup`), `rust-toolchain.toml`(stable, `wasm32-unknown-unknown` 타깃, `rustfmt`, `clippy`)
- [x] git 저장소 초기화, `.gitignore`(`target`, `node_modules`, `var`, 빌드 결과), `core.fileMode false`
- [x] 환경 준비 스크립트: Cargo의 `target`을 WSL 홈 아래에 만들고 저장소에는 심볼릭 링크를 둠 (architecture.md 7절)
- [x] Cargo 워크스페이스와 크레이트 다섯 개(`shared`, `client-core`, `client-wasm`, `server`, `tools`)의 뼈대, 브라우저 껍데기 `web/`의 뼈대
- [x] 전체 검사 스크립트 (architecture.md 8절의 구성)
- [x] `config/balance.toml`과 범위 검증 로더 (M0에 필요한 수치부터)
- [x] 맵 텍스트 형식의 로더와 검증 (design.md 4절의 글자 전부 인식), 벽이 몇 개 있는 작은 시험용 맵
- [x] `shared`: 캐릭터 이동과 지형 충돌(`step_character`), 시드 난수, 상태 해시, 프로토콜 타입
- [x] `server`: 방 코드 입장, 방마다 태스크 하나인 고정 틱 루프, 입력 대기열과 검증, 매 틱 상태 전송, 연결별 지연 주입 옵션, 정적 파일 제공
- [x] `client-core`: 서버 메시지 해석, 자기 예측과 보정, 타인 보간, 서버 시각 추정, 화면에 그릴 상태 만들기
- [x] `client-wasm`과 `web`: WebAssembly 빌드와 연결, 방 코드와 이름을 넣는 접속 화면, 맵과 캐릭터 그리기, 입력 수집, 디버그 표시(왕복 지연, 보정 크기)
- [x] `tools`: 화면 없는 테스트 클라이언트 (`client-core`를 네이티브로 써서 무작위로 움직이며 예측 오차를 기록)
- [x] `CLAUDE.md`의 명령어 절 채우기

**범위 밖:** 시야, 공격, 역할 구분, 대기실 기능, 봇. 이 단계의 캐릭터는 모두 같은 속도로 움직이는 원입니다.

Rust와 TypeScript의 경계(architecture.md 5절)는 이 단계에서 굳습니다. 뒤 마일스톤의 규칙은 전부 이 경계의 Rust 쪽에만 추가되어야 하므로, 여기서 TypeScript가 계산을 떠맡기 시작하면 이후 내내 규칙이 두 벌이 됩니다.

**자동 확인**
- 단위 테스트: 벽을 통과하지 못함, 모서리에서 미끄러짐, 대각선 이동이 더 빠르지 않음, 같은 입력열이 같은 해시를 냄
- 정해진 입력열을 네이티브 빌드와 WebAssembly 빌드(Node에서 실행)로 각각 돌려 최종 상태 해시가 같음
- 빌드 산출물이 `/mnt/e`가 아니라 리눅스 쪽 파일시스템에 쌓임 (`target`이 가리키는 실제 경로의 파일시스템 종류로 확인)
- `web/`의 소스에 이동, 충돌, 판정 계산이 없음 (경계를 넘어온 값을 그리기만 하는지 직접 읽어서 확인하고 보고에 근거를 적음)
- 테스트 클라이언트 4개를 왕복 지연 150ms(±30ms 흔들림)로 60초 돌렸을 때
  - 연결 끊김과 예외가 없음
  - 지형 충돌만 있는 상황에서 자기 예측 오차(서버 상태에 미처리 입력을 다시 적용한 위치와 예측하던 위치의 차이)가 최대 1cm 이하
  - 서버의 틱 처리 시간과 틱 간격의 분포를 출력
- 입력을 두 배 빠르게 보내는 클라이언트의 캐릭터가 60초 동안 정상 클라이언트보다 5% 넘게 멀리 가지 못함

**사람 확인**
- 브라우저 창 두 개로 같은 방에 들어가면 서로의 움직임이 보인다
- 지연 150ms를 주입한 상태에서 자기 캐릭터가 누르는 즉시 움직이고, 끌려가거나 튀지 않는다
- 상대 캐릭터의 움직임이 끊기지 않는다

## M1. 1대1 추격

**목적:** 탑다운에서 추격이 재미있는지 확인합니다. 이 게임에서 가장 중요한 관문입니다. 여기서 재미가 없으면 뒤 단계는 의미가 없으므로, 사용자가 직접 해 보고 계속할지 판단합니다.

**작업**
- [ ] 맵 타일 전체 종류의 이동·시야·공격 규칙 (design.md 4절)
- [ ] 첫 맵의 초안: 루프 구조물 종류별로 최소 하나씩 (창틀이 있는 높은 벽, 판자가 있는 낮은 벽, 판자가 있는 작은 높은 벽 덩어리, 빈 구역)
- [ ] 살인마: 회전 속도 제한, 공격(준비 동작, 판정, 후딜), 창틀 넘기, 판자 부수기, 기절
- [ ] 생존자: 건강·부상·다운 상태, 피격 후 가속, 넘기(빠른·느린, 반복 제한), 판자 내리기
- [ ] 살인마와 생존자의 충돌 (막기만 가능, 밀어내기 없음)
- [ ] 시야 판정 함수, `view_for`로 거른 상태 전송, 클라이언트의 시야 밖 어둡게 덮기, 접근 경고
- [ ] 1대1 시험 방식: 생존자가 다운되면 3초 뒤 시작 지점에서 건강 상태로 다시 시작 (이 단계 전용 임시 규칙), 추격 통계 표시(조우부터 첫 피격, 다운까지 걸린 시간)
- [ ] 단순한 추격 봇 두 종류 (혼자서도 양쪽 역할을 시험할 수 있게)
- [ ] `tools`: 루프 시뮬레이터. 구조물을 정해진 경로로 도는 생존자 봇과 쫓는 살인마 봇을 화면 없이 돌려 구조물별로 첫 피격과 다운까지 걸린 시간을 표로 출력

**범위 밖:** 수명 게이지, 구속, 구출, 소생, 치료, 리스폰 규칙, 목표, 승패, 대기실.

**자동 확인**
- 단위 테스트: 공격 판정(사거리와 각도의 경계, 벽 뒤, 가장 가까운 한 명만 맞음, 다운된 대상은 안 맞음), 판자(내리는 틱에 걸쳐 있으면 기절, 같은 틱의 적중과 기절이 둘 다 성립, 내린 뒤 아무도 끼지 않음), 창틀(빠른·느린 조건, 반복 제한), 벽 종류별 시야(높은 벽은 양쪽, 낮은 벽은 살인마만 가림)
- 정보 누출 테스트: 무작위 배치 다수에서 `view_for` 결과에 시야 밖 상대가 들어 있지 않음
- 루프 시뮬레이터: 모든 구조물에서 살인마 봇이 90초 안에 생존자 봇을 맞힘. 결과 표를 보고에 포함. 맞히지 못하는 구조물이 있으면 맵이나 수치의 문제이므로 원인을 보고
- 결정론 테스트와 M0의 자동 확인이 계속 통과

**사람 확인** (두 사람이 10분 이상, 또는 한 사람이 봇을 상대로)
- 조우부터 다운까지 추격 한 번이 평균 20~40초인가
- 쫓는 쪽과 도망치는 쪽 모두 매 순간 판단할 것이 있는가
- 높은 벽 구조물에서 보이지 않는 상대의 위치를 읽는 재미가 있는가
- 살인마의 회전 제한과 부채꼴 시야가 답답하기만 하지 않은가
- 판자 기절, 넘기, 공격 적중이 억울하게 느껴지지 않는가 (지연 100ms 주입 상태에서도)

## M2. 4인 라운드

**목적:** 라운드가 시작부터 승패 결정까지 끊김 없이 도는 상태를 만듭니다.

**작업**
- [ ] 수명 게이지, 구속(가장 먼 구속 지점으로 이동), 구출, 소생, 치료, 보호 상태, 전원 무력화 규칙 (design.md 7, 8, 10절)
- [ ] 사망 집계, 리스폰(대기 시간, 지점 선택과 선택 불가 규칙, 강제 리스폰), 대기 중인 생존자의 시야
- [ ] 목표(동시 2곳 활성, 협동 보너스), 제한 시간, 승패와 시간 판정 (design.md 3, 9절)
- [ ] 살인마에게 보내는 생존자 정보의 익명화 (design.md 11절)
- [ ] 대기실(역할 선택, 빈자리 봇 채우기, 시작), 결과 화면
- [ ] 봇의 전체 행동 (architecture.md 4절), 접속 끊김과 재접속
- [ ] 화면 표시 전부 (architecture.md 5절)
- [ ] 첫 맵 완성 (목표 6, 구속 4, 리스폰 4, 판자 10~12)
- [ ] 라운드 기록과 리플레이 검증 도구, 라운드 종료 시 지표 요약 (design.md 15절)
- [ ] M1의 임시 규칙 제거

**범위 밖:** design.md 14절의 항목 전부, 외부 배포.

**자동 확인**
- 단위 테스트: design.md 3절과 7~11절의 규칙마다 하나 이상. 특히 게이지가 멈추는 조건, 구속 시 게이지가 0 이하면 그 자리에서 사망, 전원 무력화, 보호가 풀리는 조건, 리스폰 지점 선택 불가와 그 예외, 시간 판정의 동점 처리
- 봇 넷(살인마 1, 생존자 3)으로 화면 없는 라운드 200회: 예외와 멈춤이 없고, 모든 라운드가 세 종료 조건 중 하나로 끝남. 종료 조건별 비율, 라운드 길이 분포, design.md 15절의 지표를 표로 보고
- 리플레이 검증: 기록된 라운드 10개를 다시 돌려 최종 해시가 일치
- 정보 누출 테스트: design.md 11절 표의 "알 수 없음" 항목 전부, 익명화 포함
- 봇 셋과 테스트 클라이언트 하나가 지연 150ms 상태에서 라운드를 끝까지 진행
- 생존자 수 설정을 4로 바꾼 화면 없는 라운드 20회도 끝까지 진행 (규칙 코드가 인원수를 가정하지 않는지 확인하는 것이고, 이 구성의 밸런스는 보지 않음)
- M0, M1의 자동 확인이 계속 통과

**사람 확인**
- 사람 두 명 이상과 봇으로 라운드를 끝까지 할 수 있다
- 처음 하는 사람이 화면 표시만 보고 지금 무엇을 해야 하는지 안다
- 구속된 아군의 위치와 남은 게이지가 한눈에 보인다
- 리스폰 지점을 고르는 흐름이 막히지 않는다

## M3. 플레이테스트 반복

**목적:** 네 명이 실제로 해 보면서 수치를 맞추고, design.md 15절의 위험이 실제로 일어나는지 봅니다. 이 단계는 사용자가 이끌고, 작업하는 쪽은 요청받은 것을 지원합니다.

**작업** (요청이 있을 때)
- [ ] 다른 사람이 접속하는 방법 마련. 방식은 사용자가 정합니다. 외부에 공개되는 일이므로 사용자 확인 없이 배포하거나 터널을 열지 않습니다.
- [ ] 여러 라운드의 기록을 모아 지표를 요약하는 도구
- [ ] 수치 조정과 그 효과를 봇 라운드로 미리 확인
- [ ] 플레이테스트에서 나온 버그 수정

**통과 기준** (사용자가 판단)
- 살인마 승률 40~60%, 라운드 길이 6~10분
- design.md 15절의 위험 지표가 받아들일 수 있는 범위
- 네 명이 한 판 더 하자고 한다

이 뒤의 방향(역할 로테이션 점수제, 운반 추가, 살인마 능력 등)은 M3의 결과를 보고 사용자가 정합니다.

## 진행 기록

작업 세션이 끝날 때마다 아래 형식으로 맨 위에 덧붙입니다. 다음 세션은 이전 세션의 기억이 없으므로, 이 기록과 체크박스가 이어받는 유일한 수단입니다.

```
### YYYY-MM-DD (마일스톤)
- 한 일:
- 자동 확인 결과: (통과한 것, 실패한 것과 그 출력)
- 남은 일:
- 알려진 문제:
- 사용자가 확인하거나 정해야 할 것:
```

### 2026-11-28 (M0, PR #1 두 번째 리뷰 반영)
- 한 일: 두 번째 리뷰 지적 11건(Important 2, Nit 9)을 모두 확인했고 모두 맞아서 고쳤음.
  - `client-core`가 유한하지 않은 `now_ms`를 세션에 넘기지 않게 함.
  - 서버가 틱을 건너뛰면 그만큼 입력 대기열에 따라잡기 허용량을 줌.
  - 실행 중 다시 읽은 설정을 시작 때의 메시지 한도와 비교함.
  - `net.input_burst` 하한을 2.0으로 올림.
  - 지연선 테스트를 tokio 가상 시간으로 바꿈.
  - 화면 준비가 실패하면 이유를 보여 주고 입장 화면으로 돌아가게 함.
  - `check.sh` 경계 검사가 rg 오류를 실패로 셈.
  - 명단 전송 실패를 루프 뒤에 처리함.
